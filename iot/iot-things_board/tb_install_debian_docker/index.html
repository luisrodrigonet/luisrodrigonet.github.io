    Instalando o ThingsBoard com Docker no Debian (com dados persistentes)

    Este artigo mostra, passo a passo, como instalar e configurar o ThingsBoard em uma máquina Debian usando Docker e garantindo a persistência dos dados em pastas locais, pronto para uso em projetos reais de IoT.

    Quem começa a utilizar com ThingsBoard muitas vezes sobe o contêiner “rápido” e, na primeira reinicialização da máquina ou atualização, descobre que dashboards, dispositivos e dados simplesmente sumiram.

    Isso acontece porque, por padrão, o container Docker guarda tudo dentro do próprio sistema de arquivos efêmero do contêiner; ao removê-lo, você perde a base de dados e os logs, a menos que tenha volumes configurados corretamente.

    Agora imagine esse cenário em um ambiente de produção:

    • Um servidor Debian recebendo dados de sensores, medindo consumo de energia ou monitorando uma linha de produção, e, por um descuido de configuração, um simples docker compose down -v faz desaparecer semanas de histórico.

    Além disso, sem uma estrutura organizada de pastas locais, fica difícil fazer backup, monitorar espaço em disco, ou mesmo migrar a instalação de ThingsBoard para outra máquina sem dor de cabeça.

    Atenção :

    Se você roda ThingsBoard em Docker sem volumes mapeados para pastas locais, está a um comando de apagar toda a sua instalação – inclusive a base de dados.

    1️⃣ Apresentação¶

    Este guia vai mostrar exatamente como montar um ambiente sólido em Debian, onde o ThingsBoard roda dentro de um contêiner Docker, mas todos os dados críticos (banco de dados e logs) ficam em diretórios locais bem definidos.

    A abordagem segue as boas práticas recomendadas pela documentação oficial do Docker para persistência de dados e pelo ecossistema do ThingsBoard para uso de imagens como thingsboard/tb-postgres com volumes mapeados.

    Nesta seção, você verá uma visão geral do que será construído, para já ter um mapa mental claro antes de partir para os comandos.

    Ao final do artigo, você terá:

    • Um servidor Debian pronto para rodar Docker e Docker Compose.
    • Um diretório de projeto com um docker-compose.yml organizado para o ThingsBoard.
    • Pastas locais no host (/opt/thingsboard/...) com dados persistentes, mesmo que o contêiner seja recriado.
    • Comandos para subir, parar, atualizar e verificar o estado do ThingsBoard de forma segura.

    Observação :

    O foco aqui é ThingsBoard Community Edition em instância única (single-node), ideal para laboratórios, POCs e pequenas implantações on‑premise.

    🔖 Entendendo os componentes¶

    Antes de partir para a prática, vale alinhar rapidamente o papel de cada componente e como eles conversam entre si.

    • Debian: sistema operacional do host, responsável por rodar o Docker e armazenar os dados em disco físico.
    • Docker: plataforma de contêineres que empacota o ThingsBoard e suas dependências em uma unidade isolada.
    • ThingsBoard: plataforma IoT que expõe painéis, APIs e integrações, executando dentro do contêiner.
    • Volumes/bind mounts: mecanismo do Docker para manter dados fora do ciclo de vida do contêiner, permitindo que sobrevivam a recriações e atualizações.

    Dica :

    Em termos simples: contêiner é descartável, dados não. Por isso, volumes e bind mounts são a peça-chave deste tutorial.

    🔖 Escolhendo a imagem do ThingsBoard (PostgreSQL vs Cassandra)¶

    O ThingsBoard oferece três tipos principais de imagens Docker de instância única, variando principalmente pelo banco de dados usado.

    De acordo com a documentação, as opções são:

    • thingsboard/tb-postgres: instância com banco PostgreSQL integrado, recomendada para servidores pequenos com pelo menos 1 GB de RAM e carga baixa (algumas mensagens por segundo), sendo 2–4 GB mais confortável.

    • thingsboard/tb-cassandra: instância com Cassandra, mais performática e recomendada para cargas maiores, exigindo pelo menos 4–6 GB de RAM, com 8 GB sendo ideal.

    • thingsboard/tb: instância com banco HSQLDB embutido, não recomendada para avaliação séria ou produção, usada apenas para desenvolvimento e testes automatizados.

    Para um servidor Debian típico de laboratório ou pequeno ambiente de produção, este artigo utilizará thingsboard/tb-postgres, que equilibra simplicidade e robustez.

    🔖 Arquitetura do que será construído¶

    Nesta seção, você verá um panorama da arquitetura final para entender desde já como cada peça se encaixa.

    A arquitetura final será:

    • Um diretório de projeto, por exemplo /opt/thingsboard-docker.
    • Dois subdiretórios principais para persistência:
    • /opt/thingsboard-docker/data → mapeado para /data dentro do contêiner (base PostgreSQL + dados da plataforma).
    • /opt/thingsboard-docker/logs → mapeado para /var/log/thingsboard dentro do contêiner (logs).
    • Um arquivo docker-compose.yml que:
    • Usa a imagem thingsboard/tb-postgres.
    • Expõe as portas HTTP, MQTT e CoAP para o host.
    • Define variáveis de ambiente da fila (queue), usando a opção em memória para simplificar.

    Dica :

    Vários tutoriais oficiais de ThingsBoard usam exatamente essa abordagem de volumes mapeados, com diretórios locais vinculados a /data e /var/log/thingsboard no contêiner para garantir persistência.

    2️⃣ Realizando a instalação¶

    🏗️ Pré-requisitos: o que você precisa antes de começar¶

    Aqui você confirma se seu ambiente Debian está pronto para seguir o passo a passo sem interrupções.

    Você vai precisar de:

    • Um servidor ou VM com Debian recente (por exemplo, Debian 11 ou 12), com acesso root ou sudo.
    • Acesso à internet para baixar imagens do Docker Hub.
    • Usuário com permissão para executar sudo (ou rodar tudo diretamente como root).

    Dica :

    Se possível, use uma máquina dedicada ou uma VM apenas para o ThingsBoard, deixando claro que o consumo de memória e disco será dominado pela plataforma IoT.

    🏗️ Passo 1 – Preparar o Debian para o Docker¶

    Nesta seção, você verá como garantir que o Debian está com Docker e Docker Compose corretamente instalados.

    Atualize o sistema:

    Atualizando o sistema
    sudo apt update && sudo apt upgrade -y

    Instale os pacotes básicos do Docker :

    Realizando a instalação do Docker
    sudo apt install -y ca-certificates curl gnupg
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/debian/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg

echo \
"deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/debian \
$(. /etc/os-release && echo "$VERSION_CODENAME") stable" | \
sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

    Adicione seu usuário ao grupo docker (opcional, para não precisar de sudo a cada comando):

    Adicionando o grupo docker
    sudo usermod -aG docker $USER
newgrp docker

    Atenção :

    Após adicionar o usuário ao grupo docker, faça logout/login (ou reinicie a sessão SSH) para que a permissão seja aplicada.

    Verifique se o Docker está respondendo:

    Verificando o funcionamento do docker
    docker --version
docker compose version

    Se ambos retornarem versões, o ambiente Docker no Debian está pronto para seguir para o próximo passo de configuração do ThingsBoard.

    🏗️ Passo 2 – Criar a estrutura de pastas para dados persistentes¶

    Aqui você definirá as pastas locais onde o Debian guardará os dados da instância do ThingsBoard, garantindo persistência.

    Crie o diretório de projeto e os subdiretórios de dados e logs:

    Configurando estrutura de pastas
    sudo mkdir -p /opt/docker/thingsboard-pgsql/data
sudo mkdir -p /opt/docker/thingsboard-pgsql/logs
sudo chown -R $USER:$USER /opt/docker/thingsboard-pgsql
cd /opt/docker/thingsboard-pgsql
sudo chown -R 799:799 data logs
sudo chmod -R 750 data logs

    Esses diretórios serão montados dentro do contêiner usando bind mounts, fazendo com que a base de dados e os logs fiquem no disco do host, independentes do ciclo de vida do contêiner.

    Observação :

    Você pode escolher outro caminho (por exemplo, /srv/thingsboard/...), mas mantenha a estrutura clara: uma pasta para dados e outra para logs, facilitando backup e monitoramento.

    Habilitando a carga do Docker junto com o sistema:

    Habilitando a carga automaticamente
    sudo systemctl enable docker.service
sudo systemctl enable containerd.service
sudo systemctl  status docker.service
sudo systemctl status containerd.service

    🏗️ Passo 3 – Criar o arquivo docker-compose.yml¶

    Nesta seção, você vai montar o coração da instalação: o docker-compose.yml que descreve a instância ThingsBoard e como ela usará as pastas locais.

    Dentro de /opt/thingsboard-docker, crie o arquivo:

    Criando o arquivo
    nano docker-compose.yml

    Cole o conteúdo a seguir como exemplo base:

    Adicionando as configurações do docker
    services:
  thingsboard:
    image: thingsboard/tb-postgres
    container_name: thingsboard
    restart: always

    ports:
      - "7070:7070"
      - "8080:8080"       
      - "9090:9090"
      - "1883:1883"       
      - "5683-5688:5683-5688/udp"  

    environment:
      TB_QUEUE_TYPE: in-memory

    volumes:
      - ./data:/data
      - ./logs:/var/log/thingsboard

    A ideia de montar diretórios locais em /data e /var/log/thingsboard segue o padrão usado na documentação de exemplos de ThingsBoard com Docker, onde volumes locais são associados a esses caminhos no contêiner para garantir persistência.

    Dica :

    Se você quiser usar outra fila (por exemplo, Kafka) em vez de in-memory, isso é possível, mas exige serviços adicionais no docker-compose.yml. Para começar, mantenha TB_QUEUE_TYPE: in-memory para simplificar.

    🏗️ Passo 4 – Subir o ThingsBoard com Docker Compose¶

    Agora que o docker-compose.yml está pronto, é hora de inicializar o ThingsBoard e deixar o serviço rodando no Debian.

    Dentro de /opt/thingsboard-docker, execute:

    🐧 Iniciando o docker
    docker compose up -d

    O Docker fará o download da imagem thingsboard/tb-postgres e iniciará o contêiner, mapeando as portas e volumes definidos no arquivo de composição.

    Acompanhe os logs para saber quando a aplicação terminar de subir:

    🐧 Verificando o log do docker
    docker compose logs -f

    Quando as mensagens de inicialização desacelerarem e não houver mais erros, o ThingsBoard estará pronto para acesso via navegador.

    Atenção :

    A primeira subida pode demorar alguns minutos, especialmente porque a imagem é grande e o banco PostgreSQL precisa ser inicializado dentro do contêiner.

    🏗️ Passo 5 – Acessar a interface web do ThingsBoard¶

    Com o contêiner rodando, é hora de validar se a aplicação está realmente no ar.

    No navegador, acesse (ajuste o IP conforme o seu servidor Debian):

    http://SEU_IP_OU_HOST:9090

    Você deve ver a tela de login do ThingsBoard Community Edition; os tutoriais oficiais indicam o acesso via porta HTTP exposta no host, usando a porta mapeada no docker-compose.yml.

    As credenciais padrão normalmente são:

    • Usuário (System Administrator): sysadmin@thingsboard.org
    • Senha inicial: sysadmin

    Obsercação :

    A qualquer momento, você pode verificar o status do contêiner com: 

    docker compose ps

    3️⃣ Como a persistência de dados funciona neste setup¶

    Nesta seção, você entenderá, em detalhes, por que os dados não se perdem mesmo que o contêiner seja recriado.

    Quando você mapeia ./data:/data e ./logs:/var/log/thingsboard, o Docker está criando um bind mount, onde o diretório no host substitui o diretório interno do contêiner; assim, tudo que o ThingsBoard grava em /data e /var/log/thingsboard acaba sendo gravado diretamente no sistema de arquivos do Debian.

    A documentação do Docker reforça que volumes e bind mounts existem fora do ciclo de vida do contêiner: se o contêiner for destruído, o conteúdo do diretório montado permanece intacto no host.

    🛰️ Exemplo prático: recriando o container sem perder nada¶

    Aqui você verá, passo a passo, um cenário controlado para testar a persistência de dados e ganhar confiança na configuração.

    1. Com o ThingsBoard já em execução, crie um dashboard de teste, cadastre um dispositivo e salve algumas configurações.

    2. Em seguida, derrube o contêiner sem apagar volumes:

    🐧 Parando o contêiner
    cd /opt/docker/thingsboard-pgsql
docker compose down
    1. Verifique que as pastas continuam no Debian:
    🐧 Verificando o conteúdo das pastas
    ls data
ls logs
    1. Suba o serviço novamente:
    🐧 Reiniciando o contêiner
    docker compose up -d
    1. Acesse a UI e confira se o dashboard de teste continua lá – isso confirma que os dados foram lidos das pastas locais mapeadas.

    Dica :

    Caso você use docker compose down -v, os volumes anônimos seriam destruídos; com bind mounts apontando para pastas específicas, o risco de exclusão indevida é bem menor, pois os diretórios permanecem no host mesmo após esse comando.

    🛰️ Boas práticas para backup e manutenção¶

    Nesta seção, você verá recomendações para deixar seu ambiente pronto para produção, pensando em backup, limpeza e monitoramento.

    Algumas boas práticas recomendadas em cenários de Docker com dados persistentes incluem:

    • Backup regular das pastas de dados e logs (/opt/thingsboard-docker/data e /opt/thingsboard-docker/logs) usando tar, rsync ou soluções de backup corporativas.
    • Monitoramento de espaço em disco, especialmente no diretório onde os dados são armazenados, para evitar que o host fique sem espaço.
    • Rotação de logs: integrar os logs do ThingsBoard com ferramentas de log centralizado (como journald, Loki, ELK), se necessário.

    Atenção :

    Nunca faça limpeza manual dentro de data/ sem entender o que está apagando. A pasta contém a base de dados do ThingsBoard; exclusões indevidas podem corromper a instância.

    🛰️ Variando o setup: diretórios dedicados em outro disco¶

    Se seu servidor Debian possui um disco separado para dados (por exemplo, montado em /mnt/dados), você pode apontar as pastas do ThingsBoard para lá.

    Basta ajustar o diretório de projeto ou os caminhos de bind mount, por exemplo:

    🐧 Ajustando o caminho
    volumes:
  - /mnt/dados/thingsboard/data:/data
  - /mnt/dados/thingsboard/logs:/var/log/thingsboard

    Essa abordagem segue o mesmo princípio descrito na documentação de volumes do Docker, em que um diretório arbitrário do host é usado como backend de armazenamento para os dados persistentes do contêiner.

    Dica :

    Colocar os dados em um disco separado facilita snapshots, migrações de VM e amplia a vida útil do SSD/HDD principal do sistema operacional.

    🛰️ Como atualizar o ThingsBoard mantendo os dados¶

    Aqui você verá um fluxo simples para atualizar a imagem do ThingsBoard sem perder sua base de dados e configurações.

    Um fluxo comum de atualização com Docker é:

    1. Parar o serviço:
    🐧 Parando o contêiner
    cd /opt/thingsboard-docker
docker compose down
    1. Baixar a versão mais recente da imagem:
    🐧 Baixando a imagem atualizada
    docker pull thingsboard/tb-postgres
    1. Subir novamente, ainda usando o mesmo docker-compose.yml e as mesmas pastas locais:
    🐧 Reiniciando o contêiner
    docker compose up -d

    Como os dados ficam em bind mounts no host, não dentro do sistema de arquivos do contêiner, a nova versão da imagem do ThingsBoard continua utilizando os mesmos arquivos de banco de dados e de configuração.

    Observação :

    Antes de grandes atualizações de versão, sempre leia as notas de release do ThingsBoard para verificar se há migrações específicas de banco ou mudanças de esquema.

    4️⃣ Encerrando: o que você construiu¶

    Você acabou de montar um ambiente de ThingsBoard sobre Debian e Docker com foco em segurança e persistência de dados, seguindo as boas práticas de volumes e bind mounts recomendadas pela documentação do Docker e pelos exemplos oficiais do ThingsBoard.

    Com esse setup, é possível evoluir para cenários mais complexos: trocar a fila em memória por Kafka, migrar PostgreSQL para um serviço externo, ou até escalar a arquitetura para múltiplas instâncias, mantendo o mesmo princípio central que evita perder dados a cada mudança de contêiner.
